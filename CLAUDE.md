# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is an R package called `markermd` that provides a Shiny-based interface for grading assignments submitted as git repositories containing Quarto (`.qmd`) documents. The package includes template creation functionality and validation rule systems for automated grading workflows. Document parsing is built on the `q2r` package; the legacy `parsermd` dependency has been removed. Quarto `.qmd` is the primary format; `.Rmd` documents are read the same way (knitr chunk headers are normalized before parsing, see `use_qmd`).

## Architecture

The package is designed around two main interfaces:

### Core Functions
- **`mark()`** - launches the main grading application for collections of student repositories
- **`template()`** - launches the template creation application for single assignments
- **Git operations**: Uses `gert` package for all git interactions  
- **Document parsing**: Uses the `q2r` package to parse qmd files into a Pandoc AST. Knitr-style chunk headers (`{r label, opts}`) are rewritten to Quarto `#|` form by `normalize_knitr_chunks()` before parsing, since q2r/pampa rejects them (error Q-2-36); the rewrite returns a `line_map` attribute (the file line of each parsed line) that `parse_assignment_document()` uses to add an "is line N of the file" hint to any diagnostic whose line moved, and that the Grade tab's Source view uses (`map_ranges_to_original()`) to highlight the file as written. `mark()` parses one document per repository, chosen by `find_repo_assignment()` like `validate_project()` and `parse_project()` (`parse_repo_documents()`), never the first qmd found anywhere in the repo
- **UI framework**: Modern Shiny app using `bslib` for layout and styling

### Application Architecture

1. **Template Creation Interface** (`template()` function):
   - Interactive AST tree visualization for document structure exploration
   - Question-based organization system with node selection capabilities
   - Validation rule system for each question with multiple rule types
   - S7 class-based state management for questions and rules
   - Template saving/loading functionality

2. **Grading Interface** (`mark()` function): 
   - Collection-based workflow for multiple student repositories
   - Template-driven validation and scoring
   - Repository comparison and navigation
   - Validation result visualization
   - Five tabs: Assignments (the landing page; one per-repository table with the repo's links, validation status, grading progress, per-question scores and total, and the class summary pinned beneath as column footers), Grade (grading: the content pane beside the current question's rubric; tab value `grade`), Rubric (every question's rubric edited in one place, tab value `rubric`: `mark_rubric_editor_ui()` and `output$rubric_editor_ui` in the same rubric module, so both tabs share its item, group and grade servers; each item shows its selection count (`item_selection_counts()`) in place of its toggle and each question's scoring inputs come from `mark_grade_settings_ui()`, with the same ids as the grade widget's popovers. Both tabs draw the rubric from the same handles under their own id prefixes (`rubric_module-grade-...`, `rubric_module-editor-...`; `rx$view_id()`), so both can be on the page at once; each view redraws on structural changes and when its tab is entered, and the editor is drawn only while the Rubric tab is shown; the Rubric tab's scoring inputs are the grade widget's with an `editor_` prefix (`mark_grade_settings_ui()`) and the grade server saves either set; `add_item_to()` / `add_group_to()` take the question; a question's handles are built lazily by `ensure_question_loaded()` the first time it is shown, the Rubric tab opens, or something is added to it; new item and group ids are minted above `used_item_ids()` plus the ids in memory (`rx$new_ids()`); the Rubric tab header has its own YAML import / export controls, `editor_import_file` and `editor_export_all`, sharing the Grade tab's handler), History (one timeline of the project's snapshots and its activity log, filtered by kind; see `mod_mark_history.R`, whose `history_timeline_rows()` merges `activity_rows()` into the snapshot rows; the timeline takes the full width and a click on a row (reactable `onClick`, reported to `open_entry`) opens the entry's detail in an xl modal, which branches on `selected_id()` (a snapshot, with pin / restore / export / delete in its header; the restore, export and delete dialogs have a Back button to the detail) versus `selected_activity()` (an activity entry, with a Snapshot before button)), an optional Terminal tab (`mark(terminal = TRUE)` or a named list of commands; a `shinyterm` tabset, from Suggests, whose "+" menu starts a shell, `claude` or `codex` in the project root, see `mod_mark_terminal.R`), plus a navbar status link showing, on two lines beside a camera, the selection events recorded since the latest snapshot and its age. The app-wide repo selection is changed only through the `select_repo()` helper in `mark-app.R`; the table's score cells (which open the repo and question in the Grade tab) and the rubric's navigation sync go through it. The table's validation marker instead opens a modal with that repo's rule results (`show_validation_modal()`, which does not move the app-wide selection): the validate module's cards plus a question shortcut select in the modal header, and a Re-check button that re-parses and re-validates that one repository (`recheck_repo()`, which updates the `collection_rv` / `validation_rv` / `errors_rv` reactive values every display reads, so a submission repaired while the app is open shows its new state), namespaced to the validate module, whose labels carry a coloured ✓/✗ via a selectize render function and which scrolls to the question's card through the `markermd_scroll_to` custom message, expanding it first if collapsed. The module's script lives once in the page head (`mark_validate_script()`); each card's header carries its status and rule results and its body (the matched content) is a Bootstrap collapse, collapsed by default; the expanded question names are reported to the module's `expanded_questions` input, which the render reads under `isolate()` so a later opening keeps the same cards expanded. The shortcut select starts empty (a placeholder) on every opening, so only an actual choice scrolls. `validation_shown` is bumped on each opening so the results render into the new modal DOM, and a node preview (which replaces the modal) has a Back button that re-opens it. Repository names in the table are plain text, not buttons.

### Input Handling
`template()` accepts any of: an initialized markermd project directory (authors against the project's key repo, preloads the template stored in the project database, and saves edits back into that database), a path to an assignment file (`.qmd`/`.Rmd`), a directory containing one (matched by the `filename` glob), a saved template (`.yaml`/`.yml`), an in-memory `markermd_template`, or a GitHub `<owner>/<repo>` (cloned into `local_dir`). `mark()` takes an initialized markermd project directory (one containing `.markermd/config.yml`; see `init_project()`) and sources everything from that config: student repos under the configured `repos/` dir, the grading template (stored in the DB), the SQLite DB at `<root>/.markermd/markermd.sqlite`, and per-repo rendered HTML reports ("artifacts") resolved from the configured `artifacts:` directories (`resolve_repo_artifacts()` in `utils_artifacts.R`). An optional `template` argument (object or `.yaml` path) overrides the stored one. The grading template is stored in the project's SQLite database (the canonical store), as a JSON blob under the `metadata` table's `template` key; YAML is an optional import/export format via `template_import()` / `template_export()` (the converters live in `R/template-serialization.R`, validated against the JSON Schema in `inst/schema/markermd-template.json`). The assignment document is referenced by `source.path` (a relative path resolves against the enclosing project root first, `enclosing_project_root()`, then the template file's directory, then the working directory) and re-parsed on load to regenerate the AST, which is never stored. Bad inputs raise specific, actionable errors, and loading a template whose `format_version` predates the current `markermd_template_version()` errors with a message to recreate it.

## Coding Style

- **Assignment operator**: Always use `=` for assignment, never `<-`
- **Package dependencies**: Always use explicit namespace prefixing (e.g., `q2r::parse_qmd()`, `gert::git_clone()`) rather than importing functions
- **String construction**: Prefer `glue::glue()` over `paste()` or `paste0()` for constructing long text strings, especially when building HTML, CSS, or other formatted content. In this case long strings should only be multiline strings or strings with multiple variables being inserted.
- **Glue templates**: When using `glue::glue()` to generate CSS or JavaScript code, always use `<<` and `>>` as delimiters (`.open = "<<", .close = ">>"`) instead of the default `{` and `}` to avoid conflicts with JavaScript/CSS syntax and confusion with brace escaping.
- **Documentation**: Do not use roxygen style function documentation for non-exported functions - internal functions can have comments documenting their usage and parameters but this should not be done using roxygen style comments as this results in Rd files that are not wanted as part of the package.

## Documentation Style for Non-Exported Functions

Internal functions should use regular comments (not roxygen) with this format:

```r
# Brief description of what the function does
#
# parameter1: Description of parameter1
# parameter2: Description of parameter2

function_name = function(parameter1, parameter2) {
  # function body
}
```

**Key formatting rules:**
- Start with a brief description using regular `#` comments
- Include an empty comment line `#` between description and parameters
- Format parameters as `# parameter_name: Description`
- Include an empty line between comments and function definition
- No function title line needed
- No `@return` documentation needed

## Module Architecture

### State Management Pattern
All major Shiny modules follow a consistent S7 object-based state management pattern:

- **Question Module** (`mod_question.R`):
  - Manages `markermd_question` S7 object as reactive state (the single source
    of truth both row machines write into)
  - Handles node selection from AST tree interactions
  - Wires the rules and filters row machines onto its session
  - Returns reactive question object and node management methods

- **Rules / filters row machines** (`mod_question_rules.R` / `mod_question_filters.R`):
  - Structural twins over keyed row lists (filters are two-level: groups
    holding conditions), reading the structured ids built by the pure UI
    builders in `mod_rule.R` / `mod_filter.R` directly off the module input
  - Row keys are stable: minted from a monotonic counter when a row is
    created and never reused or renumbered, so a row's input ids stay bound
    to that row for its whole life and the list order alone carries the row
    order (the question state holds the rules and filters as unnamed lists in
    that order). No input is frozen around a re-render and nothing is
    re-indexed on delete; an event for a key no longer in the list (a second
    click on an already deleted row) is dropped
  - Shared shape: capture-all pending edits before any structural change,
    then bump a structural-only render trigger
  - The shared mechanics (`make_render_trigger()`, `make_seen_registry()`,
    `sync_keyed_observers()`) live in `mod_question_rows.R`; the seen
    registry notes a multiselect once it has reported, and `forget()` drops a
    deleted row's key

### Validation Rule System
- **Rule Verbs** (`rule_verbs()`): "has at least", "has at most", "has between", "has content", "lacks content", "has name"
- **Node Types** (`rule_node_types()`): the friendly node-kind names from `q2r_node_kind()` (Heading, Markdown, Chunk, Code block, Raw Block, HTML comment, Div, Bullet list, Ordered list, Block quote, Table, Figure, Horizontal rule, Definition list, Line block) plus "Any node". A raw block that is nothing but `<!-- ... -->` comments (a skeleton placeholder, a write-up left inside it, a markermd repair marker) is its own kind, "HTML comment", never a "Raw Block", so a `[Markdown, Raw Block]` write-up rule counts `{=html}` write-ups but not comments; `is_html_comment_block()` in `utils_q2r.R` and the matching `has_text()` predicate in `filter-helpers.R` share one regex (`html_comment_only_regex`) so rules and filters agree. "Any node" stays literal and still counts comments
- **Values**: Type-specific validation values (numeric ranges, text patterns)
- **Built-in validation**: S7 class validators ensure rule consistency and type safety
- **Section-based matching**: a question's selected node indices map to heading-section paths; validation selects the matching sections from each repository's AST and applies the rules (see `utils_template.R`); a heading's section also ends at the first heading another question of the template selects (`other_question_heading_ids()`, the `stop_ids` argument of `get_question_ast()` / `heading_section_indices()`), in grading, the editor's badges and tree (`question_covered_indices()` feeds `tree_selection_state(covered =)`), mark()'s cards, Source view and report highlight, and `assignment_outline(template =)`

## Development Notes

- Document parsing is built on the `q2r` package (local working copy at /Users/rundel/Desktop/Projects/q2r). q2r has a Rust component, so installing markermd via `devtools::install()` will, because of the `Remotes: rundel/q2r` entry, reinstall q2r from GitHub and may clobber a newer local q2r build. To develop against the local q2r, install markermd with `R CMD INSTALL .` (which does not process Remotes) after installing q2r from its local path.
- The flat-list / heading-section model the rest of the package relies on comes from `q2r_flatten()` (in `R/utils_q2r.R`), which walks the nested Pandoc AST into an ordered, heading-nested, indexable node list. `build_ast_tree_structure()`, node selection, and section-based validation all key on this.

## UI Behavior Notes

- **Node Selection**: In the template interface tree view, headings are the selectable units (a question targets the document sections beneath the selected headings). Clicking a heading's text or its circle toggles selection of that heading and the section under it; non-heading content is not directly selectable and shows a static "Selected via parent heading" indicator when it falls under a selected heading. Headings have no preview button; content nodes (markdown, chunks, etc.) have a magnifying-glass button that opens a read-only preview modal. The tree's buttons are plain markup with no Shiny input bindings, so browser tests click them with `click_tree_node()` and read the patched tree with `tree_dom_html()` (`helper-template-entry.R`).
- **Tree node labels** come from `q2r_node_label()` / `q2r_node_detail()` in `utils_q2r.R`: e.g. `Heading [h2] - Title`, `Chunk [r] - label (N lines)`, `Raw Block [html]`, and `Markdown` with the text content on a smaller second line.

- **Visual Consistency**: All selected elements use the same green color (`#28a745`):
  - Selected circle SVG buttons
  - Selected node text in the tree
  - Selected node index numbers in the questions panel
  - Focus outlines for interactive elements

## Shiny Reactive Programming Guidelines

- **Avoid unnecessary local copies**: Don't make local copies of reactive values (e.g., `current_questions = questions_reactive()`) unless actually necessary for functionality. Use the reactive value directly in expressions instead to avoid creating extra reactive dependencies and improve performance.

## UI Guidelines

- Rather than using the direct html all icons should use `fa_icon()` (`utils_ui.R`; the same markup as `shiny::icon()` without its per-call name lookup and dependency, which each app attaches once via `fa_dependency()`); icons are decorative and rendered `aria-hidden`, so put any accessible name on the surrounding control, or `cached_icon()` for fixed icons in hot render paths
- Use `shiny::modalDialog()` (with `easyClose = TRUE`) for modals rather than hand-rolling modal markup. Note that under bslib (Bootstrap 5) `shiny::showModal()` relies on the `bootstrap.Modal(...).show()` script that `modalDialog()` already includes to actually display the modal.

## UI Layout Guidelines

- **Layout System**: Use bslib's `layout_columns()` for all column-based layouts instead of Shiny's `fluidRow()` and `column()`
- **Column Specification**: Use the `col_widths` parameter to specify column proportions (e.g., `col_widths = c(6, 6)` for equal columns)
- **Responsive Design**: Take advantage of bslib's responsive breakpoints when needed
- **Style Preservation**: Apply custom styles to content divs rather than layout containers when possible
- **Bootstrap Utility Classes**: Whenever possible use bootstrap utility classes rather than direct CSS styles to adjust the appearance of our shiny apps.
